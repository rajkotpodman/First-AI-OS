## 2. Boot & Initialization Pipeline

The First AI OS boot sequence transitions from physical/virtual hardware to the Python intelligence layer in five deterministic stages:

### Stage 1: ISOLINUX / Hybrid MBR Bootloader
- The storage media (USB flash drive or CD-ROM ISO) boots via the El Torito specification or Hybrid MBR partition record generated by `xorriso` with `isohdpfx.bin`.
- `isolinux.bin` executes and reads `boot/isolinux/isolinux.cfg`.
- Loads `ldlinux.c32` and `menu.c32` to present the 3-second selection menu.
- Passes kernel boot arguments:
  ```text
  console=tty1 quiet initrd=/boot/initramfs-virt modules=loop,squashfs,overlay alpine_dev=cdrom:iso9660
  ```

### Stage 2: Linux Kernel & Initramfs Expansion
- The selected kernel (`vmlinuz-virt` or `vmlinuz-lts`) initializes physical CPU registers, ACPI tables, and storage controllers (`virtio`, `ata`, `nvme`, `usb`).
- Initramfs unpacks into memory, loading required live modules: `loop.ko`, `squashfs.ko`, and `overlay.ko`.
- The live media search script scans storage controllers for `.alpine-release`, mounts the CD-ROM, and exposes `/live/rootfs.squashfs`.

### Stage 3: OverlayFS Rootfs Synthesis
To support a persistent yet stateless operational model, First AI OS mounts the filesystem as an OverlayFS stack:
- **Lower Layer (Read-Only):** `/live/rootfs.squashfs` containing the base Alpine Linux rootfs and injected `/opt/ai-os` code.
- **Upper Layer (Read-Write):** A dynamic tmpfs in RAM (or designated physical storage partition if persistent boot is configured).
- **Merged Root:** Switched via `pivot_root` into `/sysroot` as the primary `/`.

### Stage 4: OpenRC Init System Execution
Init is handed over to `/sbin/openrc` using standard Alpine runlevels:
1. `sysinit`: Mounts virtual filesystems (`/dev`, `/dev/pts`, `/proc`, `/sys`), initializes device manager `mdev`, and loads device drivers.
2. `boot`: Checks local filesystems (`localmount`), configures loopback networking, and runs system loggers (`syslog`).
3. `default`: Launches the background network stack, starts the `docker` daemon, starts Ollama background workers, and launches the `/etc/init.d/ai-os` service.

### Stage 5: TTY1 Direct Login & Python Master Orchestrator
- In `/etc/inittab`, `tty1` is configured to run BusyBox `getty` with the `-n -l` flags:
  ```inittab
  tty1::respawn:/sbin/getty -n -l /usr/bin/ai-os 38400 tty1 linux
  ```
- This skips username and password challenges, immediately executing `/usr/bin/ai-os` (symlinked to `/opt/ai-os/src/main_orchestrator.py`).
- Fallback standard login consoles remain accessible on `tty2`, `tty3`, and `tty4` for administrative and debugging access.

## 3. Storage Layout & Persistence Architecture

First AI OS divides storage into volatile operational zones and persistent state zones:

| Directory Path | Filesystem Type | Purpose & Persistence Guarantees |
| :--- | :--- | :--- |
| `/` | OverlayFS (SquashFS + RAM) | Read-only OS core with volatile copy-on-write scratchpad. |
| `/opt/ai-os/` | Lower SquashFS Layer | Immutable system application code, plugins, and test suites. |
| `/workspace/` | Persistent OverlayFS / Mount | User software projects, Git repositories, and local development trees. |
| `/workspace/.ollama/` | Persistent Mount | Downloaded GGUF / SafeTensor model weights. |
| `/workspace/.ai_os/` | Persistent Mount | Personal memory profiles (`memory.json`) and session context. |
| `/var/log/` | Volatile Tmpfs | Ephemeral runtime logs, rotating security audit records. |
| `/tmp/` | Volatile Tmpfs | Build artifacts, disposable scratch scripts, and IPC sockets. |

## 5. Security Model & Sandboxed Execution

Security in First AI OS is structured in defensive concentric rings:

```text
               ┌──────────────────────────────────────────────┐
               │              UNTRUSTED CODE                  │
               │   ┌──────────────────────────────────────┐   │
               │   │      Seccomp-BPF Syscall Filter      │   │
               │   │   ┌──────────────────────────────┐   │   │
               │   │   │   Linux Capabilities Dropped │   │   │
               │   │   │   ┌──────────────────────┐   │   │   │
               │   │   │   │ Cgroups Limits:      │   │   │   │
               │   │   │   │ - Max 2 CPU cores    │   │   │   │
               │   │   │   │ - Max 2 GB RAM       │   │   │   │
               │   │   │   │ - Max 256 PIDs       │   │   │   │
               │   │   │   │ - Read-Only Rootfs   │   │   │   │
               │   │   │   └──────────────────────┘   │   │   │
               │   │   └──────────────────────────────┘   │   │
               │   └──────────────────────────────────────┘   │
               └──────────────────────────────────────────────┘
```

1. **Static Command Policy Vetting:** Before any shell command generated by the AI agent is submitted to the kernel, `security_daemon.py` matches it against destructive regex patterns (`rm -rf /`, raw disk formatting, firmware writing).
2. **Containerized Sandboxing (`sandbox_runner.py`):** Code execution tests triggered by the self-healer or user prompts run in disposable containers with `--cap-drop=ALL` and the custom [`configs/seccomp_profile.json`](file:///e:/AI%20OS/configs/seccomp_profile.json) applied.
3. **Audit Ledger:** Every command invocation, timestamp, process ID, and exit status is signed and recorded in `/var/log/ai_security_audit.json`.

## 6. Hardware Acceleration & Neural Inference Pipeline

The `hardware_manager.py` subsystem interfaces with host hardware through multiple driver interfaces:
- **NVIDIA GPU Detection:** Invokes `nvidia-smi` and queries `pci.ids` to extract GPU model, compute capability, total VRAM, and free VRAM.
- **AMD ROCm Detection:** Queries `/dev/kfd` and `rocm-smi` for Radeon ROCm acceleration layers.
- **Intel / DRM:** Scans `/dev/dri/renderD128` for Intel QuickSync and integrated GPU capabilities.
- **CPU Diagnostics:** Reads `/proc/cpuinfo` to detect vector extensions: `avx`, `avx2`, `avx512f`.

Based on available hardware, AI OS dynamically computes the inference tier and writes `/etc/ai_os/ollama.env` before starting the inference server:
- Sets `OLLAMA_NUM_PARALLEL`, `OLLAMA_NUM_THREADS`, and `OLLAMA_GPU_LAYERS`.

## 7. Zero-to-GUI Dynamic Desktop Transition

When the user requests graphical output (`gui` or `toggle_gui.sh`), First AI OS performs a dynamic runtime transition:
1. `gui_expander.py` queries Alpine package manager (`apk`) to ensure `sway`, `waybar`, `foot`, `seatd`, and `mesa` are installed.
2. Injects pre-configured styling from [`configs/sway/`](file:///e:/AI%20OS/configs/sway/).
3. Starts the `seatd` daemon to handle hardware display and input seat multiplexing without root privileges.
4. Executes `sway` on `/dev/tty1`, replacing the TTY agent with the Wayland compositor.
5. Upon user exit (`Super+Shift+E`), Sway cleanly shuts down, the seat is released, and `inittab` respawns the master TTY AI agent on `tty1`.
